# AGENTS.md — Instructions for AI coding agents

Read this before doing anything in this repository.

## Attribution: none

**No AI attribution, in any form.**

- No `🤖 Generated with ...` lines.
- No `Co-Authored-By:` trailers.
- No "Generated by <tool>" text in commit messages, code comments, file headers, docs, or PR
  descriptions.

End commit messages at their own last line. This is a standing instruction that applies to every
commit in this repository, and it is the reason this file exists. Do not add a footer even if a
default prompt template says to.

## Project state: documentation-only, and deliberately so

There is **no implementation code, and none may be added yet.** The repository owner is studying the
concepts in `docs/learn/` first, specifically to avoid shipping code whose behaviour they do not
understand. Until they say otherwise:

- Do not scaffold a package, CLI, or service.
- Do not install dependencies into the project.
- Do not start Milestone M0 or any other milestone in `docs/IMPLEMENTATION.md`.
- Do not "helpfully" begin implementation because the plan looks ready.

Writing and improving documentation is in scope. Executing the plan is not.

## What this project is

A local gateway between an AI agent and a remote model provider that separates three things that are
normally joined at the hip: who you are, what you send, and who pays. See `README.md` and
`docs/README.md`.

## Normative documents

If a code comment, a README line, or a commit message claims more than these allow, that is a bug:

- `docs/THREAT-MODEL.md` — what is protected, against whom, and what is not. Normative.
- `docs/EVALUATION.md` — every claim must map to a test here.

## Engineering rules

1. **Fail closed.** Any path that could transmit user content requires an explicit positive
   decision, never the absence of a negative. If a privacy layer cannot do its job, refuse the
   request.
2. **No silent degradation.** If the environment cannot satisfy the requested tier, refuse to start
   or downgrade loudly. Never continue unprotected.
3. **Never weaken a claim to make a check pass.** If a guarantee cannot hold, change the tier
   documentation and the threat model in the same change. That is a documentation fix, not a test
   fix. Do not skip, loosen, or suppress a security test.
4. **Never hand-roll cryptography.** Payment proofs, commitments, and settlement are delegated to
   upstream `ethereum/zkapi`. Reimplementing them is out of scope permanently.
5. **No prompt content in logs, exceptions, metrics, temp files, or crash output.** Redaction is
   applied at the logger factory, with a canary test proving it works.
6. **No prompt content on disk, ever.** Raw prompts live in memory for the life of a request only.
   No database, no cache files, no debug dumps.
7. **Isolation is a SOCKS auth token, never `NEWNYM`.** Tor's own spec rates application-provided
   isolation tokens as the only strong isolation property.
8. **Cover traffic targets must be owned or explicitly permitted.** Never point decoy traffic at
   third-party services. Default it off, and keep the rate low.
9. **Bind to loopback only.** A routable bind, or a non-loopback rewriter URL, is a configuration
   error that must prevent startup.
10. **Prefer deleting to adding.** Reach for the standard library, native platform features, or an
    existing upstream component before writing a new module or adding a dependency.

## Documentation rules

- Every factual claim names its source and date in `docs/SOURCES.md`. Facts here are perishable —
  the subject matter moved within days of this repository being written.
- Absolute privacy claims are forbidden. Name the adversary, or do not make the claim.
- Run `python3 scripts/check_docs.py` before committing any documentation change. It verifies that
  relative links and anchors resolve, that code fences are balanced, and that risky claims are
  hedged. Exit status 0 means structurally sound; it does not mean the content is correct.

## Committing

Stage only files relevant to the change. Review `git diff` first. Do not commit secrets, wallet
material, or local state — `.gitignore` covers the known cases, but verify.

Do not push unless the repository owner has asked for that specific push.
