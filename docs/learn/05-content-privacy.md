# 05 — Content Privacy and Rewriting

## The question

The provider has to read your prompt in order to answer it. So what does "protecting your prompt" even
mean?

## First principle

**You cannot hide a request from the party that must compute on it. You can only remove the parts that
are not needed.**

This is a different kind of privacy problem from the previous three lessons. Tor hides *where* you are;
zkAPI hides *who is paying*; cover traffic blurs *when*. All three hide the request from parties that
do not need it. The model, by contrast, needs the request. There is no cryptographic trick available:

| Approach | Why it does not solve this |
| --- | --- |
| Encrypt the prompt | The provider cannot compute on ciphertext. Not a policy choice — an arithmetic one |
| Homomorphic encryption | Lets computation happen on ciphertext in principle; not practical for large language models at any useful cost or latency today |
| Confidential compute (TEE) | Works, but shifts trust from "the provider's policy" to "a hardware vendor's attestation" — a different trust, not no trust |
| Self-host the model | Genuinely solves it. Also requires hardware most people lack, and gives up the capability of frontier models |

So for the hosted-model case, the only lever is **minimisation**: send less. Privacy here is
subtraction, and the interesting engineering is deciding *what* to subtract without breaking the task.

## The two failure modes, and why they pull against each other

Rewriting sits on a tradeoff, not on a yes/no switch:

| Failure | What happens | Who notices |
| --- | --- | --- |
| **Over-disclosure** | You send personal details the task did not require | Nobody. It is silently a privacy loss |
| **Over-removal** | You strip something the model needed to answer well | You — as a vague sense that "the AI is dumb today" |

Over-disclosure is invisible because nothing breaks. Over-removal is invisible because it looks like
model quality. **Both failures hide from casual observation**, which is exactly why this project
treats rewriting quality as something to be measured rather than felt.

## Why type-based PII scrubbing fails

The obvious approach — find personally identifiable information and delete it — is what most "private
AI" tools actually do, and it fails in both directions for the same underlying reason: **it decides
what is sensitive by looking at the information's type, ignoring the task.**

Here is the canonical example, which you can test your intuition against:

> "I'm allergic to peanuts. Suggest trail snacks for a hike."

- Asking about **snacks**: the allergy is *essential*. Removing it produces dangerous advice. Removing
  it is over-removal.
- Asking about a **Python file-renaming script**: the allergy is *irrelevant*. Sending it is
  over-disclosure.

Same sentence, same "PII category" (a health condition), opposite correct answers. **No type-based
filter can make this distinction**, because the distinguishing information is not in the span — it is
in the task.

The same blind spot cuts the other way. A pattern-matcher looking for names, emails, and phone numbers
will happily pass:

- *"I'm the only paediatric nurse at the hospital in a town of 4,000 people."* — no PII pattern matches,
  and it is one of the most identifying sentences possible.
- *"My company is migrating off the system we built in 2019; here's the config file…"* — the config
  file is a fingerprint, and it is not "PII".

## What better rewriting looks like: task necessity

The framing that improves on type-based filtering comes from privacy theory (Contextual Integrity) and
can be stated in one sentence:

> **Forward a span to the model if and only if the model needs it to answer *this* task.**

That reframes the whole problem. Instead of asking "is this sensitive?", ask "does the remote model
need this in order to help with what I actually asked?" — which is why a good rewrite is generated by a
model that understands the request, not by a regex.

The concrete instruction this project uses is a version of upstream's, which is worth understanding
because it defines what the layer can and cannot do:

| Rule | Why |
| --- | --- |
| Send **only the new user turn** to the rewriter | Limits disclosure and cost; the rewriter is a second model that also sees your text |
| Extract **task, necessary context, constraints**, then rebuild concisely | Structure first, prose second — this is reconstruction, not proofreading |
| **Preserve verbatim**: code, quotes, identifiers, paths, URLs, numbers, exact-output constraints | Paraphrasing code or a numeric limit silently changes the answer |
| **Do not** answer, add facts, resolve missing context, or soften negations | Each of these changes the request rather than protecting it |
| **Fail closed** on malformed output | A privacy layer that silently falls back to the raw prompt is not a privacy layer |

The "preserve exactly" and "never resolve missing context" rules deserve emphasis: they exist because
the tempting behaviours for a helpful model are precisely the destructive ones here. A rewriter that
helpfully completes your half-finished thought has altered your request, and a rewriter that strips a
negation ("do *not* use recursion") has inverted it.

## Two limits of rewriting that you must internalise

**1. Reduced identifiability is a goal, not a proven property.** Even after removing facts, *how* you
write is identifying: vocabulary, rhythm, punctuation habits, idiom, the way you structure a problem.
This is **stylometry**, and it is how authorship attribution works on texts with no names in them.
Paraphrasing changes some stylometric signal; whether it changes *yours* enough to matter is an
empirical question nobody has proven for this setting. Upstream's documentation says it plainly:
reduced stylometric identifiability is a **model instruction, not a proven property**. This project
repeats that rather than upgrading it into a guarantee.

**2. "No raw prompt" is a processing claim, not a diff claim.** It means every user-role text part
went *through* the rewriter and none bypassed it. It does **not** mean every character changed. If your
prompt is `def foo(x): return x`, the "privacy-preserving" rewrite is very likely the same string,
because preserving code exactly is the correct behaviour. Similarly, text you place in `system`,
`developer`, `assistant`, or tool-result messages is **outside** the rewriting path entirely — a
concrete hole for anyone who assumes the whole request is covered. Same for attachments: images,
audio, and files are retained and **not anonymised** by this design.

## The rewriter itself is a leak if you put it in the wrong place

There is a trap here that has caught real implementations, including the upstream one at the time of
research: **the rewriter makes a direct connection, outside Tor.**

Sit with the absurdity for a second. You carefully route your inference through a per-conversation Tor
circuit, then hand your *original, unrewritten* prompt to a second service over a connection that
reveals your IP directly. The most sensitive artifact in the entire pipeline — the raw text — takes the
least protected path.

The fix is structural, not a setting:

- The rewriter must be **local** (loopback), running on your machine, and
- the gateway should **refuse to start** if the configured rewriter URL is not loopback.

This is why this project's configuration validation treats a non-loopback rewriter as a hard error
rather than a warning: it is the single easiest way to accidentally build something that leaks more
than it protects.

## Why measurement is not optional here

Because both failure modes are invisible, and because the tradeoff is easy to lie about.

Consider two trivial "rewriters":

| Rewriter | Over-disclosure | Over-removal | Looks good if you publish… |
| --- | --- | --- | --- |
| Delete everything | Perfect (0%) | Catastrophic | Only the disclosure rate |
| Pass everything through unchanged | Terrible | Perfect | Only the retention rate |

**Publishing either metric alone lets a useless system look excellent.** That is why this project
requires both to be reported together, and why [../EVALUATION.md](../EVALUATION.md) §4 forbids
reporting them separately. The measurable version of the task-necessity idea is:

- **Non-essential disclosure rate** — how much sensitive-but-unnecessary material survived?
- **Essential retention rate** — how much the model needed was preserved?
- **Exact-preservation rate** — did code, numbers, paths, and constraints survive byte-for-byte?
- **Constraint retention rate** — did negations and conditions survive intact?

And a methodological rule that determines whether the numbers mean anything: **annotate the evaluation
samples before you tune the rewriter.** Labels written after seeing a rewriter's output describe that
rewriter, not the task. This is the difference between a benchmark and a justification.

## Where it breaks

**1. The task itself is disclosed.** "Low-sodium dinner ideas for a heart condition" tells the provider
something personal even with every name removed. Rewriting cannot fix this — only a local model can,
and that is a different product.

**2. Cross-session linkage through content.** Reused project documents, distinctive phrasing, the same
unusual problem from three angles — the provider can link sessions by content regardless of network or
payment hygiene. This is the residual risk this project ranks highest, because it is both likely and
hard to detect.

**3. Non-`user` text.** System prompts, tool results, attachments, and anything a client stuffs into the
wrong field are unprotected by design.

**4. Availability versus privacy.** Fail-closed means a broken rewriter means no service. That is the
correct default and it *will* occasionally be annoying, which is why tiers exist and why a downgrade
must be explicit rather than silent.

**5. Evaluation is only as good as its data.** A synthetic eval set is systematically easier than real
prompts. Any reported number must say what it was measured on.

## What this means here

- **Decision D8:** rewriting fails closed; downgrades require explicit user authorisation and are
  visible in status output; both quality metrics ship together or not at all.
- **Milestone M2** builds the rewriter *and* the harness, and the milestone does not close until the
  numbers exist — see [../EVALUATION.md](../EVALUATION.md) §2 (`SC4`, `SC5`).
- **Risk R1** in [../THREAT-MODEL.md](../THREAT-MODEL.md) ranks content-based re-identification as the
  highest residual risk. Nothing in this project eliminates it; several things reduce it.

## Self-check

1. "We remove all PII before sending your prompt to the model, so your conversations are private."
   Give one counter-example of over-disclosure and one of over-removal, and identify the missing
   concept.
2. You run an excellent local rewriter. Your gateway is configured to reach it at
   `https://rewriter.example.com`. What is the problem, and what should the software do about it?
3. A team reports "99.7% of sensitive spans removed". What single additional number do you need before
   believing the system is useful, and why?

<details>
<summary>Answers</summary>

1. Over-disclosure: *"I'm the only paediatric nurse at the hospital in a town of 4,000"* — no PII
   pattern, highly identifying. Over-removal: deleting "I'm allergic to peanuts" from a request for
   trail snacks, which the model needed to answer safely. The missing concept is **task necessity**
   (contextual integrity): sensitivity is a function of the task, not a property of the span's type.

2. The rewriter is **remote**, so your original, unrewritten prompt leaves your machine over a
   connection that reveals your IP — the most sensitive artifact in the pipeline taking the least
   protected path. The rewriter must be local. The software should **refuse to start** with a
   non-loopback rewriter URL, because this failure is silent and catastrophic and therefore must be a
   hard error rather than a warning.

3. The **essential retention rate** (and ideally exact-preservation and constraint retention). A
   perfect disclosure number is achieved trivially by deleting everything, which destroys the product.
   Reporting only one side of a two-sided tradeoff is the standard way rewriting quality gets faked.

</details>
